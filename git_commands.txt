- git stash command records the current state of your working directory and the index (staging area).
    It's kinda like your computer's copy/paste clipboard.
    It records those changes in a safe place and reverts the working directory to match the HEAD commit (the last commit on your current branch).

    git stash to save your work
    git stash list to see your list
    git stash pop apply your most recent stash entry to your working directory and remove it from the stash list
    git stash push -m | --message "message"
    git stash apply just like pop, but it will keep the stash in the stash list.
    git stash drop This will remove the most recent stash from the stash list without applying it.
    
    # Apply the third (0, 1, 2) most recent stash
    git stash apply stash@{2}

    # Remove the third most recent stash
    git stash drop stash@{2}

 - git worktree is just the directory on your filesystem where the code you're tracking with Git lives.
    .Tracked files (files that Git knows about)
    .Untracked files (files that Git doesn't know about)
    .Modified files (files that Git knows about that have been changed since the last commit)

    We've talked about:

    Stash (temporary storage for changes)
    Branches (parallel lines of development)
    Clone (copying an entire repo)

    Worktrees accomplish a similar goal (allow you to work on different changes without losing work), but are particularly useful when:
        You want to switch back and forth between the two change sets without having to run a bunch of git commands (not branches or stash)
        You want to keep a light footprint on your machine that's still connected to the main repo (not clone)

- git worktree list to list all worktrees

- git worktree add <path> [<branch>]
    <branch> is optional, it will use the last part of the path as the branch name.
    you cannot work on a branch that is currently checked out by any other working tree (main or linked)
    ruuning a git branch on your main worktree tells you if a branch is checked out in a different worktree by ( + ) prefix


** TO CLEAN UP YOUR WORKTREES

- git worktree remove <WORKTREE_NAME> OR PATH TO IT
    Removes worktree reference from the .git/ main worktree
    Fails if the worktree has uncommitted changes (unless --force is used)

    -----
    OR
    -----

- git worktree prune
    Use git worktree prune only if worktree directories were deleted manually (e.g., via rm).
    Does not delete working directories (only removes Git's internal tracking).
    Typically used after manually deleting a worktree directory (e.g., with rm -rf).
        Cleanup after manual deletion
    Safe to run; only removes orphaned metadata.

** When to Use git worktree vs. Alternatives

(Tool)	        (Best For)	                                            (Limitations)	                                (Worktrees’ Advantage)
-stash	Quick context switches (temporarily shelve changes).	Changes are hidden, not editable.	    Worktrees let you actively work on multiple changes simultaneously.
-branch	Isolating features/hotfixes (standard workflow).	    Requires checkout/switch to toggle.	    Worktrees avoid switching—parallel directories for simultaneous work.
-clone	Full isolation (e.g., experimenting safely).	        Duplicates the entire repo (heavy).	    Worktrees share the main repo’s objects (lightweight).

** Semver or Semantic Versioning v1.0.0

    It has two primary purposes:

    To give us a standard convention for versioning software
    To help us understand the impact of a version change and if it's safe (how hard it will be) to upgrade to
    Each part is a number that starts at 0 and increments upward forever. The rules are simple:

    MAJOR.MINOR.PATCH EX v1.0.0
        
        MAJOR increments when we make "breaking" changes (this is typically a big release, for example, Python 2 -> Python 3)
        MINOR increments when we add new features in a backward-compatible manner
        PATCH increments when we make backward-compatible bug fixes


        Examples:

        Starting a Project

        1.0.0 → First stable release.

        Adding a Feature

        1.1.0 → Added a new button (no breaking changes).

        Fixing a Bug

        1.1.1 → Fixed a bug where the button didn’t work on mobile.

        Breaking Change

        2.0.0 → Removed the old button (users must update their code).
